工单分流 Agent 面试演讲稿
大约 3 分钟。括号里的字不用念，是你自己看的提示。

开讲前先准备好三个窗口
1. GitHub：https://github.com/lyu24944-cmyk/ticket-triage-agent
   滚到 README 的架构图和审核台截图。
2. 审核台：若改过 web/，先 scripts\build_review.ps1。仓库根目录执行下面两行，浏览器打开 http://127.0.0.1:8000/review
   $env:RAG_BASE_URL = "local"
   .\.venv\Scripts\python.exe -m uvicorn ticket_triage.api.main:app --host 127.0.0.1 --port 8000
   检索走仓库里的三篇文档。模型用现有 .env，不要新建 Langfuse Key。审核台走 /v1。
3. Langfuse 美国云：https://us.cloud.langfuse.com
   用现有这把 Key 登录。Traces 里按版本 openai-act-v3 过滤。旧的演示记录仍是 openai-act-v2。
   退款单：https://us.cloud.langfuse.com/trace/f602e8657b113fc2488615fc5376cb2e
   问候单：https://us.cloud.langfuse.com/trace/9d0518c4e915b559d1c7e1ca9c911f7d

现场新建一张单大约要 10 秒。可以先建好再讲，也可以点下去之后接着说架构。


第一段，开场，大约 25 秒

这是一个工单分流 Agent。客服工单进来以后，模型自己决定要不要查知识库、要不要看这张工单的历史，然后起草回复。写状态必须等人工审核。通过才结案，驳回就升级。

模型只能选两个只读工具：search_knowledge_base 和 get_ticket_history，或者 finish。update_ticket_status 不在它的工具列表里，人审通过之后才由最后一步去写。


第二段，指着 GitHub README，大约 40 秒

（指架构图）

流程是固定的：入库、分类、工具调度、起草、人工审核。工具调度这一步会循环，最多四步。它看已经成功调用过什么，再决定下一步是检索、查历史，还是结束。

（指截图）

这张就是审核台。左边是待审，右边是模型写的草稿。这张退款单已经检索过，引用是 kb-billing-refund，政策编号 REF-14。下面有通过和驳回。截图停在这里，是因为通过之前，工单还不是已结案。


第三段，切到本地审核台，大约 70 秒

我在本地再走一遍。主题用「紧急退款」，正文写「我被重复扣款，需要退款」，点创建并送审。

（等草稿出来，指右侧）

类别是 billing，优先级是 high。工具调用有三次，都成功：先检索知识库，再查这张工单自己的历史，然后 finish。草稿里的引用只能来自刚才检索到的文档，这里是 kb-billing-refund。现在状态停在待审，还没有变成 resolved。

再来一张问候单。主题 Hello，正文 Just saying hi。

（指工具调用）

类别是 other，优先级是 low。它只调用了 finish，没有检索，引用是空的。知识库里没有的问题，就不该去搜，也不该编一句政策。

驳回的话，状态会变成 escalated，不会悄悄丢掉。通过才会变成 resolved。

（如果要演示重启恢复，先说这句话再停进程）

待审记录写在 SQLite 里。我把 API 停掉再启动，同一张工单还在，可以继续通过。trace 编号不变。


第四段，切到 Langfuse，大约 40 秒

同一条运行也送到了 Langfuse。我按提示词版本 openai-act-v3 过滤。换一版提示词，就用这个标签把两次运行分开。

（打开退款单那条 trace）

左边是执行顺序：分类、三次工具决策、检索、查历史、finish、起草。右边这张退款单的类别、引用、工具选择、有没有退回 stub，分数都是 1。整单大约 10 秒，两千个 token 左右。模型路径超过 2 秒是预期的，这 2 秒预算只记录，不把这次运行判失败。

（打开问候单）

问候单这边没有 search-knowledge，只有 finish。不该引用的时候，分数也是 1。


第五段，收束，大约 20 秒

评测是 40 条黄金集，进了 CI。没有 Key 的时候走关键词 stub，CI 不依赖外网模型。有模型的时候，任何一张单退回 stub，评测就失败。

DeepSeek，模型是 deepseek-flash，提示词版本 openai-act-v3。40 条的结果是：非法工具调用为 0，类别准确率 1.0，优先级准确率 1.0，引用精确率 1.0，不该引用时伪造率为 0，工具选择准确率 1.0。p95 大约 15.7 秒，只记录，不卡门禁。

送进模型的内容只有四样：当前工单、已经成功的工具结果、这一次检索到的文档、上一步的错误码。超过上下文上限时，先删最早的工具结果。工单和本次引用留到最后。


如果被问「讲一次评测抓住的事故」，大约 60 秒

三次都发生在 2026 年 10 月 24 日，模型是 deepseek-flash。黄金集没有改。

第一次，不该检索的工单去检索了。运费、学生折扣、营业时间、地址，这些知识库里没有，期望类别是 other、优先级 low、不要检索。当时类别已经对了，但模型还是去搜，优先级被标成 medium。工具选择 0.85，过了 0.70 的门，可是「知识库没有的问题不再检索」这句话还不成立。我只改了提示词：类别是 other 时必须 finish，范围外的询问用 low。这 6 条重跑之后都只 finish，引用为空。

第二次，传输中断把调度退回了 stub。提示词改完后的第一次全量，工具选择已经是 1.0，优先级是 0.90。有一张单在调度时 SSL 中断，记了 act_model_failed，退回 stub。模型这条路径要求退回次数为 0，所以这次失败。后来同一请求在传输错误时最多再试 2 次，并把「无法登录」和 cannot login 写明为 high。下一次全量各项都是 1.0，退回 0。再跑一次仍然通过，p95 是 15164 毫秒。

第三次，注入句没有改成写状态。有几条用例的正文直接要求调用 update_ticket_status。抽查调用记录，它们只检索并查看当前工单，或者只 finish。没有成功的写状态，非法调用为 0。

三次都是门禁或抽查先暴露问题，再改提示词或加重试。用例保持原样。


如果被问「为什么不做鉴权、多 Agent、再加一个工具」

这个仓库是作品集演示，不是生产系统。工具面只有三个：两个只读，一个写状态。写状态必须在人审之后。开放 shell、SQL 或任意 HTTP，评测就守不住。多 Agent 和鉴权会把这条主线冲淡。面试时我把它们说成取舍。


简历上可以贴的一句

用工单分流 Agent 做白名单工具调用：模型自行决定是否检索知识库和工单历史，写状态必须经人工审核。40 条黄金集进入 CI，非法工具调用为 0，类别准确率 1.0，优先级准确率 1.0，引用精确率 1.0，不该引用时伪造率为 0。DeepSeek（deepseek-flash，openai-act-v3）上工具选择准确率 1.0，知识库没有的问题不再检索，也没有编造引用。
